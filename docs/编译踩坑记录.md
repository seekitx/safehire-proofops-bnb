# 编译与发布踩坑记录

## 2026-09-08 — 绿云 Docker 上下文上传必须先完成

- 环境：macOS 上传 Git 候选代码到绿云 Linux，Docker 构建 SafeHire。
- 命令：`git archive HEAD | ssh <已配置服务器> 'tar -x -C <候选目录>'`，随后 `docker build -t local/proofops-safehire:<版本> <候选目录>`。
- 表现：上传持续约一分钟时过早开始构建；构建本身约二十秒成功，但容器没有新加入的 `workspace/actions.py`，前端文件指纹也不匹配。
- 原因：把有先后依赖的上传和构建错误地重叠执行，读取到了旧目录与部分新文件。
- 解决：等待上传进程明确返回成功，再重建同候选；第一次产物未上线。
- 下次更快的做法：上传成功作为构建的前置条件；候选构建后比较所有被打包的已跟踪文件 SHA-256，必须零差异才允许发布。不能只根据镜像标签或构建成功判断版本。
- 验证：候选 `07d446e` 重建后核对 309 个文件，零差异；远程三组 CI 全通过。最终线上核查另见业务发布记录。

## 2026-09-08 — 安装包路径与项目配置路径不同

- 环境：Docker 通过 pip 安装 Python 包；预检查曾使用 `PYTHONPATH=/app/src`。
- 表现：预检查能读取交付指针，正式容器却退回日志扫描；并非链上交付丢失。
- 原因：用库文件位置推导项目配置目录。正式启动从 site-packages 导入，库位置不同。
- 解决：使用服务工作目录下的 `config`，允许运营方用 `SAFEHIRE_CONFIG_DIR` 明确指定。
- 下次：除了源文件指纹，还要使用正式启动方式验证安装后的包，不能只用覆盖 PYTHONPATH 的试验容器。
- 验证：最终候选必须在不设置 PYTHONPATH 的容器中复核 #56741，再检查正式接口和工作台。
